# Design

DCP/IMF validation tool. Rust core with CLI, Tauri GUI, and a browser WASM validator.

## Layout

- `rust/crates/dcpdoctor-core`: validation engine and media tooling. Shares code via postkit (path dep) and asdcplib-rs (git).
- `rust/crates/dcpdoctor-cli`: clap CLI, all subcommands.
- `rust/crates/dcpdoctor-parse`, `-imf`: no-std-io XML parsers shared with wasm.
- `rust/crates/dcpdoctor-wasm`: browser validator; deliberately avoids postkit, uses -parse/-imf.
- `gui/`: Tauri app (drag & drop, filters, sidecar CLI).
- `web/`: embedded WASM validator page, deployed to Pages.
- `schemas/`: XSDs for schema-validate (xmllint).
- dci-ctp (sibling repo) holds the DCI CTP test suite that runs against this tool.

## What is implemented and wired

- Structure validation: ASSETMAP/PKL/CPL parse, duplicate IDs, asset existence, PKL hash verify, PKL to ASSETMAP cross-reference.
- XSD schema validation (always on when schemas are available): every CPL/PKL/ASSETMAP is validated against the SMPTE/Interop XSDs via xmllint, emitting `xml_schema_violation`. Schema-path driven (`schema::locate_schema_dir`): `DCPDOCTOR_SCHEMA_DIR` env override, else a bundled `schemas/` dir next to the binary or in the tree; if none is found the check is skipped. The SMPTE XSDs are copyrighted so they are referenced, not vendored; point the env var at a SMPTE/Interop XSD set with a `catalog.xml` (ClairMeta bundles one under its package `xsd/`). The root element picks the document type and the namespace bound to that root element picks the standard (Interop = digicine.com), so a SMPTE CPL that declares the digicine CC-CPL namespace on a caption track still validates against the SMPTE schema. The catalog resolves cross-schema imports offline.
- UUID format check (`invalid_uuid`): every `urn:uuid:` identifier in the DCP's XML must be a well-formed RFC 4122 UUID (standard-agnostic).
- MXF partition structure (`mxf_invalid_structure`, SMPTE 377-1: header/footer/closed-complete) under `--check-mxf`/`--strict`, alongside the other MXF-reading checks.
- 4K frame rate (`picture_invalid_frame_rate`, ST 429-2 §8.2 Table 1) under `--check-mxf`/`--deep-j2k`: `mxf::check_picture_frame_rate_mxf` reads the asdcplib picture descriptor, stored width above 2048 is the 4K row, and 4K essence at a rate other than 24/1, 25/1 or 30/1 errors. Monoscopic only, which is both the scope of the "shall" and what the mono reader opens, so 3D track files yield nothing here.
- Picture size (`picture_invalid_resolution`, warning, `--strict`): `validate::STANDARD_PICTURE_SIZES` accepts the flat and scope coded images (1998x1080, 2048x858, 3996x2160, 4096x1716, the set libdcp verifies) plus the full 2K and 4K containers (2048x1080, 4096x2160). A full-container asset is legal essence, so it stays accepted.
- Picture bitrate, measured not estimated, under `--check-mxf`/`--deep-j2k`: `bitrate::analyze_picture_bitrate` walks every frame through the same `j2k::PictureEssenceReader` the codestream scan uses, trying the AS-DCP readers (mono, then 3D, where the left plus right codestream of an edit unit is one frame) and then AS-02 (the AS-02 reader would open 3D essence one eye per frame, hence last). Encrypted essence is decrypted with the run's content keys; without a covering key nothing is measured, since an AES frame is longer than the codestream inside it and a rate read off ciphertext is not the asset's rate. DCP essence over `postkit::j2k::DCI_MAX_BITRATE_MBPS` (250, DCSS 4.3.3) errors as `j2k_bitrate_exceeded`. IMP picture tracks report peak and average as INFO `picture_bitrate_measured`: no IMF specification sets a peak, so there is nothing to fail against. The IMF measurement runs before the ffprobe descriptor is consulted, so a stream ffprobe cannot see is still measured.
- App 2E picture descriptor (always on for an App 2E CPL's MainImage tracks, `app2e_picture::check_descriptor`): the AS-02 header is read through `asdcplib::as02::jp2k::MxfReader` and four things must hold. The sub-descriptor Rsiz is an IMF profile (`picture_not_imf_profile`, error: a DCI cinema Rsiz means X'Y'Z' samples, which is what imfwizard shipped for two months while this validator passed it), ColorPrimaries and TransferCharacteristic are both present (`picture_colour_missing`), the PictureEssenceCoding label is the one `asdcplib::jp2k::picture_essence_coding_for_rsize` gives for that Rsiz or its generic family label (`picture_coding_label_mismatch`), and the RGBA pixel layout pairs match the codestream components in count and depth (`picture_pixel_layout_mismatch`). A header that will not read reports `check_skipped` rather than passing. Encrypted essence is covered too, the descriptor is cleartext.
- App 2E picture samples (`app2e_picture::check_samples`, run right after the descriptor checks wherever the Rsiz already reads as IMF, since a cinema Rsiz is `picture_not_imf_profile` and would otherwise be reported twice): twelve evenly spaced frames go through `studio::walk_sampled_frames` to a scratch codestream, ffprobe names the pixel format the first of them decodes to (one profile a track file, so one probe settles all twelve), and ffmpeg reads each back as `xyz12le` where that is what ffprobe said and `rgb48le` otherwise, since asking for RGB from an X'Y'Z' codestream would apply the XYZ to RGB matrix and hide the defect. The decode drops two wavelet levels (`-lowres 2`, a quarter of the width and height), which counting ratios does not need and which takes a 3840x2160 frame from 0.22 s to 0.02 s. `sample_gamut` stays at full resolution: its share is a count of the pixels as encoded, and a reduced decode lowpasses the extremes it counts into their neighbours. A pixel counts as saturated when one channel is over 3276 and another under 256, which no X'Y'Z' of a Rec.709 colour reaches, and as bright when its largest code is over 2047, bright then counting as neutral RGB where all three channels lie within 32 codes and as an X'Y'Z' white where X'/Y' and Z'/Y' are within 0.5% of the D65 codes 3883/3960/4092 or of the DCI white's 0.9581 and 0.9822. X'Y'Z' whites in at least one bright pixel in a hundred, with no saturated pixel and ten times fewer neutral RGB ones, is `picture_samples_not_rgb` (error, the case the descriptor cannot see: an IMF Rsiz and coding label over X'Y'Z' samples). A saturated pixel or more neutral RGB than X'Y'Z' white is a clean pass. Anything else, a black or unlit track among them, is `check_skipped` naming the four counts, so an undecided sample never reads as a clean one. Essence that will not decode reports `check_skipped` too, which is where an HTJ2K track lands: ffmpeg's native JPEG 2000 decoder does not read one.
- Core CPL checks (always on): encrypted-content/KDM detection, CPL-to-ASSETMAP cross-reference, supplemental/OPL detection, marker validation (FFMC/LFMC required in strict, others recommended), MCA channel labeling, reel continuity, reel coherence, stereo 3D consistency, HFR compliance, ISDCF naming.
- Reel coherence (`reel_incoherent`, error, matches ClairMeta `check_cpl_reel_coherence` / SMPTE ST 429-2 8.7): within one CPL every per-reel essence parameter the CPL carries must hold a single value across all reels that have it. Checks picture edit rate / frame rate / frame size (ScreenAspectRatio) / resolution / encryption, sound edit rate / encryption / channel count / sample rate, and subtitle edit rate. Encryption is keyed off `<KeyId>` presence (what makes ECL32, one clear picture reel among encrypted ones, incoherent). Values are only collected where the essence is present, so a track missing on some reels is not a mismatch; MXF-probe keys (resolution/channels/sample rate) are read where the CPL carries them but SMPTE CPLs usually keep them in the MXF.
- OV-aware supplemental validation (IMF and DCP): `validate --imf <supp> --ov <ov>` resolves a supplemental CPL's track-file references across both packages (supplemental ASSETMAP + OV ASSETMAP). A ref found in either passes; a ref in neither is `cross_ref_broken`. Without `--ov`, any locally-unresolved ref is reported as `supplemental_ov_not_provided` (warning) rather than a hard `cross_ref_broken`: this matches ClairMeta, which classifies a CPL with any asset missing locally as a version file (VF) referencing an external OV, and a legitimate VF ref and a corrupt one are indistinguishable without the OV. Supply `--ov` to turn genuinely broken refs (present in neither package) back into `cross_ref_broken` errors. VF detection is therefore structural (missing local ref), not keyed on an OPL marker, so real-world VF packages without that marker are handled. Threaded via `VerifyOptions.ov`. The shared resolver (`resolve_track_ref`/`RefStatus`/`validate_track_refs_ov`) lives in `dcpdoctor-imf` and is reused by the IMF path, the DCP path, and the wasm binding. Surfaces: CLI, REST (`ov` field), and the wasm binding `validate_imf_supplemental` (OV asset ids passed from JS, since the browser has no filesystem).
- XML-DSig signature verification, plus embedded X.509 certificate chain linkage and expiry checks (self-contained DCI trust model: leaf to root within the DCP's own certs).
- Deep DCI / SMPTE ST 430-2 certificate-rule compliance (`cert_rules.rs`, wired into `signature::verify_signature` for signed packages): per-cert signature algorithm (sha256WithRSA), RSA 2048-bit / exponent 65537, Basic Constraints (cA matches CA-vs-leaf role), Key Usage (keyCertSign for CAs, digitalSignature for the leaf), dnQualifier == base64(SHA-1(public-key BIT STRING)), a permissive CN role-distinctness check, and Organization (O) coherence across the chain. Emits `certificate_*` codes.
- BV2.1 full application-profile checks behind `validate --bv21`.
- Subtitle timing and required-element checks, plus glyph coverage: every code point a cue uses must have a glyph in the font the document loads. Interop resolves the font from the `LoadFont URI` attribute, SMPTE ST 428-7 from the asset urn the `LoadFont` element carries (looked up in the ASSETMAP), and MXF-wrapped ST 429-5 timed text from the fonts embedded as ancillary resources.
- Bv2.1 timed-text content limits (line length, line count, cue duration and spacing, caption charset) run on `MainSubtitle` tracks and on caption tracks named either `MainClosedCaption` (what the digicine CC-CPL schema declares and real Bv2.1 packages ship) or `ClosedCaption`, with the stricter caption limits on the latter two. Both caption spellings are also in the CPL-to-ASSETMAP cross-reference scan, so a caption track's asset id resolves like any other external asset.
- Deep J2K analysis and DCI checks, frame-qc, auto-qc (blackdetect/freezedetect/astats). A picture MXF is read frame-0 first through the asdcplib OP-Atom reader, which yields the real codestream markers (RSIZ, COD, code-block, wavelet) for AS-DCP essence. AS-02 (IMF, OP1a) picture MXFs are rejected by that reader and fall back to ffprobe: dimensions, bit depth and per-frame bytes come from the MXF descriptor, the profile is guessed from the width, and the marker-derived fields stay unset. Both paths are covered by `j2k::as02_tests`, which wraps the IMF 4K fixture codestream as AS-02 through postkit `mxf_wrap` and asserts the OP-Atom reader rejects it and the ffprobe result carries the right dimensions and 4K profile guess, with the 2K guess covered by a descriptor written straight through the asdcplib AS-02 writer. Both need ffprobe, which CI installs on every runner.
- Loudness measure/normalize, mxf-extract, diff (with `--fingerprint` perceptual picture compare), info, watch, fix with dry-run (fix suggestions via fixes.rs).
- checksum-verify with real hash + size checking (`--no-hash` still checks sizes).
- imf-compliance runs real per-platform delivery-spec checks (netflix/disney/amazon/apple/cinema2k/cinema4k/broadcast) plus generic verify.
- hdr-validate (hdr10/hlg/dolby-vision) with MaxCLL/MaxFALL checks, driven from a video file's stream and frame side data through ffprobe.
- `validate --hdr` (`premium::detect_hdr_metadata`): the transfer and colour primaries come from the picture essence descriptor through asdcplib, so ST 2084 and the ST 2067-21 HLG UL are read as bytes rather than mapped by ffprobe first, with the ffprobe stream metadata as the fallback for anything that is not a JPEG 2000 track file. MaxCLL and MaxFALL come from the CPL ExtensionProperties, which is where ST 2067-21 clause 7.5 puts them and where the wizards write them: no MXF essence descriptor has an item for either. `hdr_metadata_summary` (info) carries the transfer, primaries, mastering display and light levels; `hdr_metadata_invalid` reports a MaxFALL above its MaxCLL (error), a MaxCLL above the mastering display maximum (warning), and light levels declared for an HLG composition, which clause 7.5 defines for the PQ colour systems only (warning).
- `validate --atmos` (`premium::parse_atmos_iab`): the essence type comes from asdcplib, so ST 429-18 Dolby Atmos data essence reports the MaxObjectCount, MaxChannelCount and version of its DolbyAtmosSubDescriptor, ST 2067-201 IAB essence is reported as detected with no object count (its descriptor carries none), and PCM sound draws nothing. Needs no ffprobe, which lists no stream for either wrapping.
- `av-sync <dcp_dir>`: each reel's picture and sound compared as the CPL declares them, reporting the entry-point offset and the duration difference in frames and milliseconds at the reel's edit rate. The file-pair form (`--video`/`--audio`) still compares two container durations.
- frame-compare resolves each IMP's picture asset; an ffmpeg run producing no frames is a hard error.
- KDM validation (not generation), theater profiles, timeline SVG, manifest comparison, batch summary.
- JSON/HTML reports, standalone `schema-validate` command, Photon bootstrap with IMF-only gating.
- Content keys for encrypted essence, resolved once per run by `validate::build_content_keys` from `--kdm` plus `--recipient-key` and threaded into every essence reader as `kdm::ContentKeys`. Both package kinds go through it: a DCP's AS-DCP essence and an IMP's AS-02 track files. A KDM that will not unwrap with the given recipient key errors as `kdm_required` and yields no keys, so nothing reads garbage. The keys are never logged, never on a command line, and the unwrapped material zeroes on drop.
- KDM validity window: `kdm_expired` (error) and `kdm_not_yet_valid` (warning) in the `kdm` command.
- KDM digest rules, run on both `validate --kdm` and the `kdm` command. The KDM schema types these elements `base64Binary` / `ds:DigestValueType`, which fixes the encoding but not the length, so the XSD pass cannot reach them. Every `<CertificateThumbprint>` in AuthorizedDeviceInfo/DeviceList must decode to a 20-byte SHA-1 digest (`kdm_thumbprint_invalid`), the optional `<ContentAuthenticator>` must too when present (`kdm_content_authenticator_invalid`), and the DCI assume-trust marker `2jmj7l5rSw0yVb/vlWAYkK/YBwk=` (DCSS 9.4.3.5, base64 SHA-1 of empty input) may not share a DeviceList with a real device thumbprint (`kdm_assume_trust_conflict`): the list either restricts playback to named devices or it does not. All three are errors. The digests are read with a namespace-agnostic quick-xml pass (`kdm::extract_digests`), since the older `extract_element` helper returns only the first match for a tag. Covered by real DCP-o-matic/libdcp KDMs under `tests/fixtures/kdm`, one per ISDCF formulation, with each negative case a mutation of one of them.
- Interop subtitles: DTD-era `<DCSubtitle>` (no namespace, `<SubtitleID>` element) is recognized, so valid Interop timed text no longer trips namespace/identifier checks meant for SMPTE DCST.
- QC report: HTML/PDF with package/track summary and optional per-track loudness.
- REST server: `GET /health`, `POST /validate {"path", "ov"?}`, legacy `POST /verify {"dcp_dir", "ov"?}`.
- Flags --studio/--netflix/--hdr/--atmos/--prores/--accessibility/--imf parsed and wired.
- GUI drag & drop, filters, sidecar (flags precede the path so they parse); web WASM validator with queue/cancel/streamed hashing.
